```markdown
## ROLE
You are [specific expert identity with bounded scope].

## CONTEXT
[Minimal necessary background. No fluff. No repetition of obvious facts.]

## TASK
[Single, atomic objective. If multiple objectives exist, decompose into sub-prompts.]

## CONSTRAINTS
- Must: [hard requirements]
- Must Not: [prohibitions]
- Ambiguity resolution: [default assumptions]

## OUTPUT FORMAT
[Exact structure expected. JSON schema, code block language, etc.]

## SUCCESS CRITERIA
[Measurable/verifiable conditions for task completion.]

## VALIDATION CHECKPOINT
Before finalizing, verify: [checklist]
```

### 2.2 Prompt Pitfalls & Anti-Patterns (Avoidance Protocol)

| Pitfall | Detection Signal | Mitigation |
|---------|------------------|------------|
| Over-prompting | >3x information needed for task | Ruthless pruning pass |
| Ambiguous scope | Multiple interpretations possible | Add explicit boundary conditions |
| Hidden assumptions | Undefined terms or references | Define all domain-specific terms |
| Output format drift | Inconsistent response structures | Lock format with examples |
| Instruction collision | Contradictory constraints | Priority ordering system |
| Token bloat | Redundant restatements | Karpathy rule: delete if meaning survives |

### 2.3 Prompt Engineering Master Class Synthesis

**Level 1: Atomic Prompts**
- Single instruction, single output type
- Zero ambiguity tolerance
- Example: `Extract all function names from this code. Output as JSON array.`

**Level 2: Chain Prompts**
- Sequential dependencies
- Each step validates previous output
- Example: `Step 1: Analyze code structure → Step 2: Identify refactoring targets → Step 3: Generate unified module`

**Level 3: Meta-Prompts**
- Prompts that generate prompts
- Self-improving loops
- Example: `Given this project's patterns, generate a prompt template for [task type]`

**Level 4: Convergent Prompts (Second-Order)**
- Multiple prompt paths converge on same output
- Cross-validation between independent generations
- Divergence triggers re-generation

## PART III: ENGINEERING GOVERNANCE PROTOCOL

### 3.1 The Six-Phase Execution Engine

```
PHASE 1: DEEP AUDIT
├── Enumerate all artifacts (files, modules, folders, subfolders)
├── Classify by type, function, dependency
├── Detect duplicates, near-duplicates, superseded chunks
├── Map interdependencies
└── Output: Complete artifact registry with metadata

PHASE 2: DECOMPOSITION
├── Break major modules into features
├── Break features into widgets
├── Break widgets into presets
├── Break presets into methods
├── Break methods into atomic operations
└── Output: Hierarchical decomposition tree

PHASE 3: UNIFICATION & ABSORPTION
├── For each duplicate/near-duplicate pair:
│   ├── Identify superior implementation
│   ├── Extract unique value from inferior
│   ├── Merge into superseding component
│   └── Log supersession with rationale
├── Apply MIT license to all absorbed components
├── Resolve naming conflicts (canonical naming)
└── Output: Unified component library

PHASE 4: RECOMPOSITION
├── Rebuild hierarchy from unified primitives
├── Ensure no orphaned components
├── Validate dependency graph (no cycles)
├── Optimize for token/performance efficiency
└── Output: Recomposed project structure

PHASE 5: SECOND-ORDER CONVERGENCE
├── Identify higher-level abstractions enabled by unification
├── Generate new meta-components that supersede groups
├── Cross-validate between independent convergence paths
├── Absorb any newly relevant external patterns
└── Output: Second-order unified architecture

PHASE 6: VALIDATION & DEPLOYMENT
├── Run all validation checkpoints
├── Verify MIT compliance
├── Generate documentation
├── Create deployment artifacts
└── Output: Production-ready meta-project
```

### 3.2 Refactoring Protocols (Detailed)

**A. Merge Protocol**
```python
def merge_superseding(component_a, component_b):
    """
    When two components serve same purpose, merge intelligently.
    """
    # 1. Identify the superior base (more complete, efficient, maintainable)
    base = max(component_a, component_b, key=lambda c: c.completeness_score)
    other = min(component_a, component_b, key=lambda c: c.completeness_score)

    # 2. Extract unique value from other
    unique_features = diff(other.features, base.features)

    # 3. Absorb unique features into base
    for feature in unique_features:
        if feature.adds_value:
            base.absorb(feature)

    # 4. Validate merged result
    assert base.passes_all_tests()
    assert base.is_mit_compliant()

    # 5. Log supersession
    log_supersession(other.id, base.id, rationale)

    return base
```

**B. Split Protocol**
When a component is doing too much:
1. Identify distinct responsibilities
2. Extract each into its own module
3. Create thin orchestrator that composes them
4. Ensure interface backward compatibility

**C. Adapt Protocol**
When a component from external source needs integration:
1. Strip external dependencies
2. Replace with internal equivalents
3. Re-license as MIT
4. Run full test suite
5. Document origin and modifications

## PART IX: KARPATHY PROMPTING GUIDELINES (Injected)

> **Principle 1**: "The best prompt is the one you don't need to write." — Maximize model autonomy where possible.

> **Principle 2**: "Delete until it breaks." — Compression algorithm for both prompts and code.

> **Principle 3**: "Explicit is better than clever." — No implicit assumptions in prompts or interfaces.

> **Principle 4**: "Test the edges, not the center." — Edge cases reveal truth about system robustness.

> **Principle 5**: "If you can't explain it in one sentence, you don't understand it." — Forces clarity.

> **Principle 6**: "The right abstraction makes the code smaller, not larger." — Beware over-engineering.

> **Principle 7**: "Build tools for yourself first." — The best components solve real, felt needs.
